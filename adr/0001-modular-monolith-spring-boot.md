# Модульный монолит на Spring Boot вместо микросервисов

## Контекст и постановка задачи

DeadlineGuard разрабатывает один разработчик (с I2 — плюс junior на 10 ч/нед), сервер — 1 vCPU и 1 ГБ ОЗУ
(REQ-PERF-003), запуск — одной командой `docker compose up` (REQ-INST-001). При этом правила эскалации
должны жить в отдельном модуле без зависимостей от веб-слоя (REQ-MAINT-001, раздел 3.5.5 SRS).
Как разбить систему на развёртываемые единицы, чтобы уложиться в ресурсы и срок и не получить «комок грязи»?

## Драйверы решения

* срок 23.12.2026 и команда из 1–2 человек;
* ресурсы сервера: 1 vCPU, 1 ГБ ОЗУ (REQ-PERF-003);
* один `docker compose up` для запуска (REQ-INST-001);
* изоляция модуля `escalation` и модульная структура кода (REQ-MAINT-001);
* транзакционная согласованность «дедлайн + напоминание» (REQ-REL-002).

## Рассмотренные варианты

* модульный монолит (один Spring Boot-процесс, модули — пакеты с явными границами);
* микросервисы (deadline-service, notification-service, ical-service);
* слоистый монолит без границ модулей (controller / service / repository на всё приложение).

## Итог решения

Выбранный вариант: «модульный монолит», потому что он единственный укладывается в 1 ГБ ОЗУ и срок, сохраняя
при этом изоляцию модулей, которую требует REQ-MAINT-001.

### Последствия

* Хорошо, потому что один процесс и одна БД — транзакции без распределённых протоколов, outbox в той же
  транзакции (ADR-0004).
* Хорошо, потому что модули `web`, `deadline`, `escalation`, `notification`, `ical`, `security`, `group`
  можно позже выделить в сервисы по границам пакетов.
* Плохо, потому что масштабируется только целиком; для 1.0 это допустимо (раздел 3.5.3 SRS).

### Подтверждение

Архитектурный тест ArchUnit в CI (REQ-BUILD-002): модуль обращается к другому только через его пакет `api`;
`escalation` не зависит от `web` и Spring MVC.

## Плюсы и минусы вариантов

### Модульный монолит

* Хорошо, потому что ~350 МБ памяти на процесс укладываются в лимит.
* Хорошо, потому что сборка, деплой и отладка — одна единица.
* Нейтрально, потому что границы модулей держатся дисциплиной и тестами, а не сетью.

### Микросервисы

* Хорошо, потому что независимое масштабирование и развёртывание.
* Плохо, потому что 3+ JVM не помещаются в 1 ГБ ОЗУ.
* Плохо, потому что нужны брокер, распределённые транзакции, трассировка — недели работы, которых нет.

### Слоистый монолит без модулей

* Хорошо, потому что самый быстрый старт.
* Плохо, потому что правила эскалации смешиваются с веб-слоем — нарушение REQ-MAINT-001.
