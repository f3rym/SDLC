# Приём обновлений Telegram через long polling вместо webhook

## Контекст и постановка задачи

Бот DeadlineGuard получает от Telegram входящие обновления только для привязки аккаунта: пользователь
переходит по ссылке `t.me/<бот>?start=<код>` и нажимает «Start» (REQ-INT-005). Исходная оценка канала
Telegram (F-08) — 18 ч, из них 4 ч — webhook с публичным HTTPS-адресом и сертификатом. В первом раунде
обсуждения плана Заказчик попросил сократить сроки (переписка в Telegram 21–22.10.2026, `plan/correspondence.md`). Как принимать обновления дешевле?

## Драйверы решения

* сокращение трудоёмкости для выпуска к 23.12.2026 в бюджете $3 000;
* хостинг ещё не выбран (OQ-1, приложение Г SRS), а разработка и тесты идут на локальных машинах без публичного адреса — webhook пришлось бы настраивать для каждой среды;
* входящих обновлений мало — только привязка аккаунта;
* исходящие сообщения (`sendMessage`) не зависят от способа приёма.

## Рассмотренные варианты

* long polling (`getUpdates` с таймаутом 30 с);
* webhook (`setWebhook` на публичный HTTPS-адрес).

## Итог решения

Выбранный вариант: «long polling», потому что он экономит 4 ч (F-08: 18 → 14 ч), не требует публичного
адреса и сертификата, а задержка в несколько секунд при привязке аккаунта для пользователя незаметна.

### Последствия

* Хорошо, потому что бот работает в любой среде — локально, на тестовом стенде, на сервере — без входящего доступа из интернета: соединения с Telegram только исходящие.
* Плохо, потому что опрашивать Telegram должен ровно один экземпляр — опрос берёт блокировку ShedLock, как
  и планировщик (ADR-0004).
* Нейтрально, потому что переход на webhook позже не затрагивает отправку сообщений.

### Подтверждение

Тест привязки аккаунта с заглушкой Bot API (TelegramLinkTest, раздел 4 SRS); POC-1 (раздел 3.5.9 SRS) —
20 сообщений из 20 доставлены с задержкой ≤ 10 с.

## Плюсы и минусы вариантов

### Long polling

* Хорошо, потому что не нужны домен, сертификат и открытый порт.
* Плохо, потому что постоянное соединение с Telegram и задержка до таймаута опроса.

### Webhook

* Хорошо, потому что обновления приходят мгновенно, без постоянного соединения.
* Плохо, потому что нужен публичный HTTPS-адрес — +4 ч и зависимость от хостинга (OQ-1, приложение Г SRS).
