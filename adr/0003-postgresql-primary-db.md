# PostgreSQL 16 с миграциями Flyway как основная БД

## Контекст и постановка задачи

Система хранит пользователей, группы, дедлайны, историю сроков, контрольные точки и очередь напоминаний.
Нужны транзакции «изменение дедлайна + постановка напоминания» (REQ-REL-002), выборка очереди несколькими
потоками без двойной обработки, хранение времени в UTC (REQ-PORT-002), автоматические миграции
(REQ-INST-002). Какую СУБД выбрать?

## Драйверы решения

* предпочтение Заказчика — PostgreSQL 16 (CON-3);
* ACID-транзакции и блокировки строк `SELECT … FOR UPDATE SKIP LOCKED` для outbox (ADR-0004);
* тип `timestamptz` для времени в UTC (REQ-PORT-002);
* бесплатная лицензия (REQ-COMP-003), официальный Docker-образ (REQ-INST-001).

## Рассмотренные варианты

* PostgreSQL 16 + Flyway;
* MySQL 8 + Flyway;
* MongoDB.

## Итог решения

Выбранный вариант: «PostgreSQL 16 + Flyway», потому что он удовлетворяет CON-3 и даёт `SKIP LOCKED` и
`timestamptz`, на которых построены очередь напоминаний и расчёт уровней.

### Последствия

* Хорошо, потому что очередь напоминаний живёт в той же БД, без отдельного брокера.
* Хорошо, потому что миграции Flyway применяются при старте приложения (REQ-INST-002).
* Плохо, потому что резервное копирование — отдельная задача (pg_dump по расписанию, REQ-AVAIL-002).

### Подтверждение

Интеграционные тесты на Testcontainers с образом `postgres:16`; миграции проверяются в CI на пустой БД.

## Плюсы и минусы вариантов

### PostgreSQL 16

* Хорошо, потому что `SKIP LOCKED`, частичные индексы (`WHERE status = 'PENDING'`), `timestamptz`.
* Нейтрально, потому что требует ~100 МБ памяти в контейнере.

### MySQL 8

* Хорошо, потому что тоже поддерживает `SKIP LOCKED`.
* Плохо, потому что нет `timestamptz` с часовым поясом и противоречит предпочтению CON-3.

### MongoDB

* Хорошо, потому что гибкая схема.
* Плохо, потому что данные реляционные (пользователь — группа — дедлайн — точки), а транзакции между
  коллекциями сложнее.
