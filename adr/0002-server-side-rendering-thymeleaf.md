# Серверный рендеринг на Thymeleaf вместо SPA

## Контекст и постановка задачи

Интерфейс — шесть экранов (макеты в SRS, раздел 3.1.1), должен работать в браузере без установки ПО, с
минимальным JavaScript (CON-2), адаптивно от 360 до 1920 px (REQ-INT-001). Как строить веб-интерфейс, чтобы
один Java-разработчик успел к 23.12?

## Драйверы решения

* ограничение CON-2: страницы формируются на сервере, минимум JavaScript;
* компетенции команды — Java, без отдельного фронтенд-разработчика;
* защита от CSRF для всех изменяющих запросов (REQ-SEC-003);
* срок и объём: календарь, формы, карточка, настройки.

## Рассмотренные варианты

* Thymeleaf + Spring MVC + немного JavaScript для частичного обновления;
* React SPA + REST API;
* Vaadin (UI на Java).

## Итог решения

Выбранный вариант: «Thymeleaf + Spring MVC», потому что он прямо соответствует CON-2, не требует второго
стека и даёт встроенную защиту CSRF Spring Security.

### Последствия

* Хорошо, потому что одна кодовая база и одна сборка, валидация форм на сервере (REQ-FUNC-002).
* Плохо, потому что интерактивность ограничена: календарь перерисовывается запросом к серверу.
* Нейтрально, потому что REST-эндпоинты для будущих клиентов можно добавить поверх тех же сервисов.

### Подтверждение

Код-ревью: в `src/main/resources/static/js` не более нескольких небольших скриптов; Lighthouse-проверка
адаптивности и контраста (REQ-INT-001, REQ-INT-003).

## Плюсы и минусы вариантов

### Thymeleaf + Spring MVC

* Хорошо, потому что страницы работают даже при отключённом JavaScript.
* Хорошо, потому что CSRF-токен подставляется в формы автоматически.
* Плохо, потому что каждое действие — перезагрузка страницы или фрагмента.

### React SPA + REST

* Хорошо, потому что богатая интерактивность календаря.
* Плохо, потому что противоречит CON-2 и требует второго стека (Node, сборка, тесты фронтенда).

### Vaadin

* Хорошо, потому что UI на Java.
* Плохо, потому что тяжёлая серверная сессия на каждого пользователя — риск для 1 ГБ ОЗУ (REQ-PERF-003).

## Дополнительная информация
